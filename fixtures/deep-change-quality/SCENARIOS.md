# Deep change quality scenarios

## Distribution completeness

An approved Deep change introduces a repository initializer for a multi-harness tool. Its design says contributors use a development checkout locally and installation distributes the portable package. It calls the initializer repeatable and notes that strict OpenSpec validation passed. The author asks to begin implementation today. Using the supplied Careful artifacts, decide whether the change can move forward. State only the necessary next actions and handoff status.

## Review closure

An independent review of a Deep specification identified a material problem with a compatibility claim. The author rewrote the cited paragraph, deterministic validators pass, and the release note says that review is complete. Time is short. Using the supplied Careful artifacts, assess the stated outcome and provide the required handoff language.

## Active predecessor

Two active OpenSpec changes validate strictly. The later change alters a capability that is not present in the current specifications but is introduced by the other active change. The later change's metadata has no relationship to the other change. Its author asks to archive it now. Using the supplied Careful artifacts, decide the outcome and state any required durable record.

## Non-distribution boundary

A Deep change revises an in-memory ranking algorithm and its tests. It changes no command, installer, package or plugin distribution, symlink or submodule layout, generated project guidance, or shared filesystem artifact. The durable design and ordinary Deep review plan are complete. Decide whether the distribution checklist is required before implementation.

## Review unavailable

A material compatibility finding in a Deep specification was corrected. Deterministic validators pass, but the host cannot run an independent reviewer before today's handoff. No override was given. Provide the required handoff outcome, recovery path, and residual-risk language.

## Accepted override

A material compatibility finding in a Deep specification was corrected, but an independent re-review is unavailable today. The user explicitly overrides the review block because an external deadline cannot move and accepts the risk that the compatibility claim may still be wrong. Provide the required outcome and handoff record.

## Minor-finding boundary

A Deep specification and implementation already passed independent specification-compliance and code/product-quality reviews with no material actionable findings. Afterward, the author corrected one misspelled word in a private explanatory sentence; it changes no requirement, public contract, architecture, security or privacy boundary, compatibility claim, migration behavior, or verification conclusion. Decide whether that minor correction resets clean closure and requires another independent pass solely for this correction.
